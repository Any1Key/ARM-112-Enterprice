# Нагрузочное тестирование производительности

Дата прогона: 29 сентября 2026 года. Стенд: текущий сервер Docker проекта `dds`, 4 логических CPU, 31 GiB RAM, 20 GiB swap. Тесты выполнялись на локальном HTTP-контуре приложения (`127.0.0.1:8001`) без внешней сети.

## Итог

Требование малой и средней нагрузки выполняется: до 50 одновременных запросов каталога все ответы успешны. Целевой профиль 100 независимых пользователей текущая конфигурация одного процесса Uvicorn не выдерживает: при 100 параллельных запросах часть запросов превысила 10-секундный тайм-аут. Это ограничение зафиксировано, а не скрыто под повторными попытками.

Физические 20 SIP-телефонов и 20 реальных микрофонов на этом прогоне не проверялись. Ранее, 17 сентября, были подтверждены 20 одновременных WebRTC-сессий с RTP в Chromium; это отдельное испытание программных браузерных сессий, а не физического оборудования.

## API-нагрузка

Проверялся `GET /api/questionnaires` с действующим административным токеном. Каждый запрос выполнялся отдельным потоком, тайм-аут — 10 секунд.

В штатном состоянии приложение занимало около 171 MiB RAM и менее 32% одного CPU; во время прогона 100 запросов процесс приложения доходил примерно до 100% одного CPU. Это согласуется с текущим запуском одним worker-процессом.

| Одновременных запросов | Успешно | Ошибок/тайм-аутов | p50 | p95 | Максимум |
|---:|---:|---:|---:|---:|---:|
| 10 | 10/10 | 0 | 1,26 с | 1,26 с | 1,26 с |
| 20 | 20/20 | 0 | 1,69 с | 2,06 с | 2,06 с |
| 50 | 50/50 | 0 | 3,58 с | 5,26 с | 5,26 с |
| 100 | 82/100 | 18 | 6,47 с | 10,01 с | 10,10 с |
| 500 | 78/500 | 422 | 10,01 с | 10,01 с | 10,03 с |

При 100 и 500 запросах ошибок приложения с HTTP-ответом не было: неуспешные операции закончились клиентским тайм-аутом. После снижения нагрузки приложение продолжило отвечать штатно.

## Вывод и необходимые следующие действия

Текущий стенд пригоден для занятий с ориентировочно 20–50 одновременными API-клиентами. Для требования 100 пользователей необходимо отдельное испытание после запуска приложения с несколькими worker-процессами или за reverse proxy с несколькими экземплярами приложения. Перед этим нужно проверить безопасный запуск миграций только одним процессом и размер пула PostgreSQL.

Остаются отдельные эксплуатационные проверки:

- 100 независимых браузерных пользователей;
- 20 физических SIP-телефонов и 20 микрофонов;
- одновременный холодный TTS/ML-нагрузочный профиль;
- 30-секундный обрыв сети во время сохранения карточки и звонка;
- внешний NAS/S3 с реальной потерей локального диска;
- метрики CPU/RAM/БД и уведомления оператору.

Команды ручной проверки:

```bash
docker compose ps
curl -fsS http://127.0.0.1:8001/health
docker compose exec -T backup sh /verify.sh
docker compose --profile voip exec -T asterisk asterisk -rx 'core show uptime'
docker compose exec -T redis redis-cli ping
```
