# Сопроводительная техническая документация

Версия документа: 29 сентября 2026 года
Проект: АРМ-112 — учебный тренажёр для подготовки операторов 112 и диспетчеров ДДС

## 1. Назначение и границы

Сервис представляет собой изолированный учебный контур. Он моделирует приём учебных обращений, заполнение карточки 112, передачу карточки в ДДС, работу со статусами и учебные голосовые контакты. Сервис не принимает реальные экстренные вызовы, не передаёт обращения в городские службы и не заменяет промышленную систему 112.

Поддерживаются три роли:

| Роль | Возможности |
|---|---|
| Администратор | Пользователи, компоненты, резервирование, восстановление, аудит, технические настройки |
| Преподаватель | Сценарии, ЕКП, заготовки и занятия, назначение студентов, мониторинг, отчёты, экспертная оценка |
| Обучающийся | Назначенные карточки 112 и ДДС, приём входящих учебных звонков/SMS, заполнение, статусы, учебные SIP-контакты |

Все данные относятся к учебному процессу. Внешние интеграции с реальными IAM, SMS, SIP-провайдерами, ПОВ-112 и городскими службами в текущую поставку не входят.

## 2. Соответствие ТЗ

Полная постатейная матрица находится в [TZ_COMPLIANCE.md](TZ_COMPLIANCE.md). В готовом контуре подтверждены:

- локальный web-сервис с PostgreSQL, Redis и Docker Compose;
- RBAC, JWT-сессии, аудит действий и разграничение материалов;
- сценарии, задания, уровни сложности, занятия и мониторинг;
- карточка 112 с ЕКП, опросными картами, таймингом, эталоном и оценкой;
- ДДС-режим с очередью, множественными входящими карточками/SMS, статусами и контактами;
- текстовые и SIP-вызовы через локальный Asterisk;
- браузерный SIP через HTTPS/WSS и аппаратный SIP-профиль через UDP;
- Silero TTS, локальная оценка свободного текста, LanguageTool и fallback без Ollama;
- отчёты, CSV, печать страницы в PDF, экспертная оценка и аудит;
- ежедневное резервирование, проверка архивов, восстановление и защитные блокировки удаления;
- адаптивный интерфейс, включая мобильную ширину и блокирующее модальное окно входящего SIP-вызова.

Не закрыты полностью требования, зависящие от внешней инфраструктуры: корпоративная IAM/LDAP, MFA, реальные территориальные полигоны, внешний SMS-шлюз, off-host backup с оповещением, многоузловая HA-схема и испытание двадцати физических SIP-телефонов.

## 3. Компонентная архитектура

```text
Браузер / аппаратный SIP-телефон
             |
      Caddy HTTPS/WSS :8443
        /              \
  FastAPI :8000      Asterisk SIP/AMI
        |              |
 PostgreSQL         RTP UDP 10000-10100
 Redis                 |
        |          Silero TTS / media volume
        +-- ML :8091 -- LanguageTool :8093
        +-- backup -> PostgreSQL dump + media + runtime
```

### Основные компоненты

| Компонент | Реализация | Назначение |
|---|---|---|
| Web/API | FastAPI, Uvicorn | REST API, HTML и статические файлы |
| UI | Vanilla JavaScript, CSS, HTML | Рабочее место, ДДС, занятия, администрирование |
| БД | PostgreSQL 16 | Пользователи, сценарии, занятия, карточки, события, отчёты |
| Кэш/очереди | Redis 7 | Резерв для фоновых задач и служебного состояния |
| VoIP | Asterisk | SIP-регистрация, звонки, AMI, запись, RTP |
| Шлюз | Caddy | HTTPS, WSS `/sip-ws`, reverse proxy к app и Asterisk |
| TTS | Silero `v5_5_ru` | Локальная генерация русской речи и ответов служб |
| ML | SentenceTransformer-сервис | Семантическое сравнение свободного текста |
| Grammar | LanguageTool-сервис | Грамматические замечания |
| Backup | Отдельный Docker-сервис | Периодические копии, SHA-256 и restore drill |

Один сервер допускает вертикальное увеличение ресурсов. Настоящее горизонтальное масштабирование требует внешнего балансировщика, общего хранилища медиа, отдельной PostgreSQL HA-схемы и согласованного SIP-маршрутизатора; это не создаётся автоматически одним `docker compose`.

## 4. Методы обработки данных

### 4.1. Сценарии и ЕКП

Классификатор импортируется из XLSX и нормализуется в версионированный снимок. Для каждого типа хранятся код, группа, признаки, вопросы и правила выбора служб. Генерация реплик использует согласованные детерминированные профили `app/scenario_profiles.py`; это обеспечивает повторяемый эталон и не зависит от доступности Ollama. Преподаватель видит черновик, проверяет реплику и эталон, затем утверждает сценарий.

### 4.2. Карточка и оценка

При старте создаётся снимок сценария, поэтому последующее редактирование каталога не меняет текущую попытку. Черновики сохраняются с ревизией и `request_id`; повторная отправка не дублирует событие. Объективные поля сравниваются правилами: тип, адрес, телефоны, признаки, службы, статусы и норматив времени. Свободный текст дополнительно сравнивается локальной ML-моделью и проверяется LanguageTool. Итог объединяет правила, время, грамматику и экспертную оценку.

### 4.3. Очередь входящих обращений

Преподаватель создаёт входящий звонок или SMS для конкретного студента. Очередь допускает несколько элементов одновременно. Активная карточка не блокирует поступление следующих обращений. В браузере входящий SIP-вызов отображается в модальном окне: пока студент не примет или не отклонит его, рабочая область недоступна. После принятия восстанавливается соответствующая карточка; новые карточки остаются в очереди.

### 4.4. SIP и аудио

Браузер получает индивидуальный SIP-аккаунт, подключается к Asterisk по WSS через Caddy и передаёт медиа через WebRTC/RTP. Аппаратный телефон использует отдельный суффикс `-hw`, UDP/5060 и RTP-порты 10000–10100. Учебный звонок не выходит во внешнюю телефонную сеть. Служебные ответы поставляются архивом `data/service_audio.tar.gz`, при запуске распаковываются сервисом `media-seed` в volume `call_media`, а новые реплики заявителя синтезируются Silero и кэшируются.

Сервисные звонки используют внутренние учебные номера. Caller ID формируется с названием службы. Номера и названия берутся из каталога, а не из внешней телефонной сети.

### 4.5. Резервирование и восстановление

Полный backup включает PostgreSQL, пользовательские вложения, записи разговоров, аудио и runtime-файлы. Архив получает SHA-256 и проходит проверку распаковки/восстановления во временную базу. Полное восстановление выполняется только после свежей страховочной копии, проверки пароля администратора и подтверждения `ВОССТАНОВИТЬ`. На время переключения операции и звонки блокируются, старые токены аннулируются.

## 5. Установка с нуля

### Требования

- Docker Engine и Docker Compose v2;
- для целевого рабочего места: Windows 10/11 или Linux, актуальный Chrome/Firefox/Яндекс.Браузер;
- для браузерного SIP: микрофон, HTTPS и доверенный корневой сертификат;
- рекомендуемый АРМ: Intel Core i5, 16 ГБ RAM, SSD 256 ГБ;
- рекомендуемый сервер с AI/TTS: от 6 ядер, 32 ГБ RAM, NVMe 512 ГБ.

### Базовый запуск

```bash
git clone https://github.com/Any1Key/ARM-112-Enterprice.git
cd ARM-112-Enterprice
cp .env.example .env
# Задайте секреты и адреса до первого запуска
docker compose up -d --build
docker compose ps
curl -f http://localhost:8001/health
```

В текущем compose приложение опубликовано на `8001`. Если используется другой checkout с прямым портом приложения, ориентируйтесь на `docker compose ps`, а не на фиксированный номер.

### Запуск телефонии и AI

```bash
docker compose --profile voip --profile silero --profile ai up -d --build
docker compose --profile voip --profile silero --profile ai ps
```

Профиль `silero` запускает локальный TTS. Профиль `ai` запускает ML и LanguageTool; Ollama требуется только для необязательных черновиков, если это явно включено конфигурацией. Для полного учебного контура со звонками и оценкой используются все три профиля: `voip`, `silero` и `ai`.

### HTTPS из локальной сети

В `.env` задаются имя, по которому браузер обращается к серверу, и адрес SIP-телефона:

```dotenv
ARM_HOST=arm112.local
SIP_PUBLIC_ADDRESS=172.16.60.98
```

На каждом Windows-клиенте в `C:\Windows\System32\drivers\etc\hosts` нужна строка:

```text
172.16.60.98 arm112.local
```

После изменения:

```powershell
ipconfig /flushdns
Test-NetConnection arm112.local -Port 8443
curl.exe -vk https://arm112.local:8443/health
```

Открывать нужно `https://arm112.local:8443`, а не IP-адрес и не имя без второй единицы в `arm112`. Корневой сертификат Caddy экспортируется так:

```bash
docker compose cp gateway:/data/caddy/pki/authorities/local/root.crt ./arm112-root.crt
```

Его необходимо установить в доверенные корневые центры Windows. В локальной сети должны быть доступны TCP 8443, TCP/UDP 3478 и UDP 10000–10100.

## 6. Ежедневная эксплуатация

1. Администратор проверяет `docker compose ps` и страницу «Мониторинг».
2. Перед обновлением запускает `docker compose exec -T backup sh /backup.sh`.
3. Для штатного обновления использует `git pull --ff-only` и пересборку без удаления томов.
4. Для проверки архива использует `docker compose exec -T backup sh /verify.sh` или `make verify-backup`.
5. При сбое сначала проверяет `/health`, логи `app`, `gateway`, `asterisk`, состояние PostgreSQL/Redis и свежесть backup.
6. `docker compose down -v` не используется в штатной эксплуатации: команда удаляет тома с базой и медиа.

Полный порядок описан в [OPERATIONS.md](OPERATIONS.md), настройка SIP — в [SIP_PHONE_SETUP.md](SIP_PHONE_SETUP.md), сценарий ДДС — в [DDS_TRAINING.md](DDS_TRAINING.md).

## 7. Безопасность и персональные данные

Учебные ФИО, номера и записи считаются персональными данными внутри локального контура. Не публикуйте PostgreSQL, Redis, AMI и RTP за пределами доверенной сети. Замените демонстрационные пароли и секреты до сетевого доступа. Используйте TLS, ограничьте ACL SIP/RTP, храните аудит не менее установленного срока и регулярно проверяйте backup. Для промышленного внедрения отдельно утвердите IAM/MFA, политику обезличивания, журналирование доступа и соответствие 149-ФЗ/152-ФЗ.

Текущая авторизация — JWT и RBAC приложения; корпоративная LDAP/IAM и MFA являются точками интеграции, а не встроенной функцией текущей поставки.

## 8. Проверка после установки

```bash
docker compose ps
curl -f http://127.0.0.1:8001/health
docker compose logs --tail=100 app
docker compose --profile voip logs --tail=100 gateway asterisk
docker compose exec -T backup sh /verify.sh
```

Ручной smoke-тест:

1. войти под преподавателем и создать/назначить занятие;
2. войти под студентом и открыть назначенную карточку;
3. подключить SIP в браузере по HTTPS;
4. создать входящий звонок преподавателем;
5. убедиться, что появляется непрозрачное модальное окно;
6. принять вызов и проверить открытие карточки;
7. завершить карточку и открыть отчёт преподавателя;
8. проверить запись разговора, аудит и состояние backup.

Автоматические и эксплуатационные результаты собраны в [VALIDATION.md](VALIDATION.md) и [PERFORMANCE_TEST_2026-09-29.md](PERFORMANCE_TEST_2026-09-29.md).

## 9. Использованные библиотеки и компоненты

Точные версии Python-пакетов фиксируются в `requirements.txt`. Основные компоненты: FastAPI, Uvicorn, SQLAlchemy, Pydantic, PostgreSQL-драйвер, Redis-клиент, httpx, PyJWT, passlib/bcrypt, openpyxl, PyMuPDF/PDF-инструменты, SentenceTransformers/torch в ML-контуре, LanguageTool, Silero-модель, Asterisk, Caddy и Docker Compose. На клиенте используются vanilla JavaScript, CSS, HTML и JsSIP; сборка фронтенда не требует npm.

Список контейнеров и переменных окружения — в `docker-compose.yml` и `.env.example`. API-контракты — в [API.md](API.md). Исходный код открыт и не обфусцирован.

## 10. Известные ограничения и план промышленного развития

- Нет реальной интеграции с городской системой 112, LDAP/IAM, SMS и внешней телефонией.
- Территориальные полигоны и часть справочника служб требуют подтверждения заказчика.
- Один Docker-хост не является полноценной HA-кластерной схемой.
- Для 100 независимых пользователей нужен отдельный multi-worker/несколько экземпляров app и повторный нагрузочный прогон с независимыми браузерами.
- Off-host backup и внешнее оповещение должны быть настроены оператором инфраструктуры.
- OCR-материалы и нестандартные сокращения требуют проверки преподавателем.

Эти ограничения не скрываются в интерфейсе и отражены в матрице соответствия ТЗ.
